# T12 independent audit

Scope is the local CI/CD implementation described in [T12 validation](t12-validation.md), reviewed against [Issue #12](https://github.com/chakirou18/final-project-AIzoomcamp-2026/issues/12) and the architecture's "Deployment, delivery and rollback" contract. Because no workflow has executed remotely, this audit can only assess configuration, scripts and their local tests. It explicitly does not claim remote acceptance.

## Findings

| Severity | Finding | Resolution |
|---|---|---|
| MEDIUM | First smoke draft asserted private paths were denied and parsed every response as JSON; the loopback-only local stack serves `/metrics` as text, so local verification crashed with `JSONDecodeError`. | Parse JSON only for JSON content types; add `--skip-private-path-check` for the loopback stack while hosted runs keep the strict default. Re-run passed. |
| MEDIUM | `check_isolation.py` could not distinguish the documented placeholder digests from a misconfigured host file. | The check substitutes a well-formed digest only when rendering the committed examples (`--image`), and still fails on unpinned images or build definitions in real host files. |
| LOW | `test_t12_pipeline.py` imported `scripts/` at collection time and broke the containerized integration run, where only `fieldops/`, `migrations/` and `tests/` are mounted. | Module-level skip when the scripts are absent. |
| LOW | The promotion gate initially required a `smoke` field inside the deployment payload, which the GitHub API cannot update after creation. | Eligibility now relies on the latest deployment status (`success` is set only after the smoke passes). |
| MEDIUM | `inputs.digest`, secrets and step outputs were interpolated directly into `run:` shell text in the promotion, rollback and release workflows (expression injection surface for a crafted dispatch input, even though `verify_digest.py` rejects malformed digests first). | Every secret, input and step output now enters shell through `env:` variables; a structural audit (`artifacts/claude/t12-workflow-audit.json`) and a line scan confirm zero `${{ }}` expressions on `run:` lines. |
| MEDIUM | `python3 -m pip install --user uv` can fail on GitHub's Ubuntu 24.04 runners when the system interpreter is marked externally managed (PEP 668). | Replaced by `pipx install "uv==0.12.19"` in all four jobs; pipx is preinstalled on hosted runners. |
| LOW | The production deployment record used the dispatching run's `GITHUB_SHA` (main head) as `ref`, not the commit of the promoted digest. | `verify_digest.py` exposes the development deployment's commit; promotion and rollback now record that commit as the deployment `ref`. |
| LOW | The scanner's own unit-test fixtures (`AKIA…`, a private-key header, a `ghp_` token) fail the CI lint job once `tests/test_t12_pipeline.py` is tracked; the pre-publication scan flagged it, but a scripting error let commit `04f3b49` go out before the fix, so it is corrected in a follow-up commit on the same branch. | Fixture source lines carry the documented synthetic marker (the written temporary file does not, so the test still exercises detection); the scan over the exact tracked set is clean. |
| INFO | The integration job's database password and session secret are literal CI-only values in `checks.yml`; they never reach a hosted environment and match the repository's existing synthetic-value convention. | Accepted; flagged by name in the secret-scan allowances. |
| INFO | `deploy.sh` runs `seed --allow-nonlocal` as an explicit release job so the synthetic personas exist in hosted environments. Production therefore holds synthetic demo users by design (approved product decision). | Documented in the T13 deployment procedure. |
| INFO | Rollback redeploys images only; contracting migrations would need an owner-approved restore. | Documented in the T13 rollback procedure. |

## Second-pass audit on `feature/t12-ci-cd` (2026-11-12)

Branch created locally from T11 `315b4491e40a19f52ae4ec06dc4de4877792cda4`; the preserved T12 files were restored byte-identically from the checkpoint before the edits above. Dependency pinning: both actions by commit SHA, uv 0.12.19, pip-audit 2.10.1, `postgres:17-bookworm` by the repository's digest. Permissions: `contents: read` at the top of every workflow; `packages: write` only in `publish`; `deployments: write` only in environment-scoped jobs; the PR path and the reusable checks reference no secrets. Concurrency: PR runs cancel superseded runs; `main-release`, `deploy-development` and `deploy-production` groups never cancel in progress. Approval boundary: the `verify` jobs carry no environment, so production secrets become reachable only inside the `production` environment job after the required reviewer approval configured by the owner. Local execution of the CI job commands: lint, unit (207), pipeline (10), dependency audit (no known vulnerabilities), image build and import, isolation render, smoke journey and `deploy.sh` dry runs passed; the host-side simulation of the integration job passed its migration smoke and 175 integration cases with no failure before Claude Code stopped the process for host memory pressure, so it is **interrupted, not failed**, and will be rerun on request. The promtool/amtool step could not be exercised from Git Bash because the shell rewrote `/bin/promtool` into a Windows path; it must be rerun with path conversion disabled once the Docker engine is available again (it was found stopped on resume and was not restarted).

No critical or high finding. The gate rejects tags, branches, malformed and never-deployed digests before any host access; secrets are reachable only inside environment-scoped jobs; both deployment workflows are serialized by concurrency group and the development job skips stale commits.

## Verdict

**CONDITIONAL GO to publish the pipeline configuration with T11/T12 once the owner authorizes the push; NO-GO for Issue #12 acceptance** until a real PR run, an automatic main→development deployment run, a blocked production gate and a failed-check denial are observed remotely. The local evidence demonstrates correctness of the configuration, scripts and gates, not the remote behaviour.
