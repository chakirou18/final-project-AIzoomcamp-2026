# T13 deployment procedure (prepared, not executed remotely)

This document describes how the FieldOps hosted environments are meant to be provisioned and operated with the T12 pipeline. **No hosting, domain, TLS certificate or credential exists yet**, so no public URL, deployment run or approval record is claimed. Everything below was prepared and verified locally only; see [T13 validation](t13-validation.md) for the actual command results and the blocked remote items. Owner approval and an approved hosting budget are required before any remote action.

## Topology

One Linux host (or two) runs Docker Engine with Compose v2 and a reverse proxy (Caddy or nginx) that terminates HTTPS. Each environment is a fully separate Compose project rendered from the same committed files:

| | development | production |
|---|---|---|
| Compose project | `fieldops-development` | `fieldops-production` |
| Database / user | `fieldops_development` / `fieldops_development` | `fieldops_production` / `fieldops_production` |
| Loopback ports (web / Grafana / Jaeger) | 18100 / 13100 / 16700 | 18200 / 13200 / 16800 |
| Subnet | 10.251.0.0/24 | 10.252.0.0/24 |
| Volumes | `fieldops-development_*` | `fieldops-production_*` |
| Image | `ghcr.io/<owner>/<repo>@sha256:<digest>` from the latest validated main | the identical digest after manual approval |
| `FIELDOPS_ENVIRONMENT` | `development` | `production` |
| Demo persona login | enabled (synthetic data) | enabled (synthetic data) |
| Pause/fault controls and On-Call demo | disabled by code (local only) | disabled by code (local only) |

`scripts/deploy/check_isolation.py` renders both environments and proves distinct projects, databases, users, ports, subnets and volume names, digest-pinned images without build definitions, and loopback-only published ports.

## Required environment variables (host-only `.env`, never committed)

| Variable | Meaning |
|---|---|
| `COMPOSE_PROJECT_NAME` | `fieldops-development` or `fieldops-production`; namespaces containers, networks and volumes |
| `FIELDOPS_IMAGE` | `ghcr.io/<owner>/<repo>@sha256:<digest>` written by `deploy.sh`; never a tag |
| `FIELDOPS_ENVIRONMENT`, `FIELDOPS_DEMO_MODE` | environment identity (`development`/`production`) and synthetic persona login (`true`); fault simulation stays local-only in code |
| `POSTGRES_DB`, `POSTGRES_USER` | distinct per environment; the password is generated inside the credential volume |
| `FIELDOPS_PORT`, `FIELDOPS_GRAFANA_PORT`, `FIELDOPS_JAEGER_PORT` | loopback-only host ports, distinct per environment |
| `FIELDOPS_SUBNET`, `FIELDOPS_TEST_SUBNET`, `FIELDOPS_BROWSER_SUBNET` | distinct networks per environment |
| `FIELDOPS_PUBLIC_HOST`, `FIELDOPS_ACME_EMAIL` | public DNS name and certificate contact for the Caddy edge |
| `FIELDOPS_PROXY_HTTP`, `FIELDOPS_PROXY_HTTPS` | edge ports (80/443 for production; distinct values when two environments share a host behind one external edge) |
| `FIELDOPS_PUBLIC_URL` | used by the smoke step and the GitHub environment URL |

Operator, recovery, webhook, agent and session keys are generated by the bootstrap jobs inside each project's credential volumes and are never placed in `.env`, GitHub or logs.

## Host layout

```
/srv/fieldops/bin/deploy.sh                      # copy of scripts/deploy/deploy.sh, root-owned
/srv/fieldops/<env>/.env                         # host-only; from deploy/environments/<env>.env.example
/srv/fieldops/<env>/repo                         # checkout of docker-compose.yml + docker-compose.deploy.yml + observability/
/srv/fieldops/<env>/releases/*.json              # append-only release and rollback records
/srv/fieldops/<env>/backups/*.dump               # pg_dump -Fc before each migration
```

The deployment SSH user may run only `sudo -n /srv/fieldops/bin/deploy.sh` (sudoers rule). Database passwords, session keys, operator/recovery/webhook/agent keys are generated inside each project's credential volumes by the existing bootstrap jobs and never leave the host.

## Public HTTPS edge (`docker-compose.proxy.yml`, `deploy/proxy/Caddyfile`)

A third Compose file adds a digest-pinned Caddy 2.10.2 reverse proxy per environment. It obtains certificates automatically for `FIELDOPS_PUBLIC_HOST` with `FIELDOPS_ACME_EMAIL`, redirects HTTP to HTTPS (keeping only the loopback liveness probe), sets HSTS and basic hardening headers, answers 404 at the edge for `/metrics`, `/internal/*`, `/demo/*` and the OpenAPI pages, forwards everything else to `web:8000` with `X-Forwarded-Proto: https`, logs JSON without cookies or authorization headers, runs read-only with all capabilities dropped except `NET_BIND_SERVICE`, and is the only service publishing a non-loopback port (80/443). The Caddyfile is mounted read-only; the admin API is disabled. Two environments on one host either use distinct `FIELDOPS_PROXY_HTTP/HTTPS` ports behind one external edge or separate hosts.

Rendered locally with `docker compose -f docker-compose.yml -f docker-compose.deploy.yml -f docker-compose.proxy.yml … config`: proxy image `caddy:2.10.2@sha256:c3d7ee5d…`, published ports 80/443 on the proxy only, web/Grafana/Jaeger on 127.0.0.1. Live TLS issuance and the edge deny rules were **not exercised** (no public host).

## Public exposure

The reverse proxy forwards `https://<host>/` to `127.0.0.1:<FIELDOPS_PORT>` and must deny `/metrics`, `/internal/*`, Grafana and Jaeger (loopback ports only, reachable through SSH tunnels). `FIELDOPS_PUBLIC_HTTPS=true` marks session cookies `Secure`; cookies are already `HttpOnly` and `SameSite=Lax`. The smoke script asserts readiness, cookie flags and that the private paths are denied through the public origin.

## Release flow

1. Merge to main → `main-release.yml` reruns every check, publishes `ghcr.io/<owner>/<repo>:sha-<commit>` and records its digest.
2. The `development` GitHub environment job (no reviewers) skips stale commits, SSHes to the host, runs `deploy.sh development <image@digest>`, records a GitHub deployment with the digest, previous digest and migration version, then runs the API-to-inbox smoke. Failure rolls back automatically ([T13 rollback](t13-rollback.md)).
3. A human dispatches `promote-production.yml` with that digest. `verify_digest.py` rejects anything that did not succeed in development; `docker manifest inspect` proves the digest exists. The `production` GitHub environment must be configured with **required reviewers** so secrets are unavailable until approval. The identical digest is released with `deploy.sh production`, smoke-tested without pausing delivery and recorded.

## Verification scripts

| Script | Purpose | Local status |
|---|---|---|
| `scripts/deploy/check_exposure.sh` | Lists non-loopback listeners (host `ss`, or `nmap` with `EXPOSURE_TARGET`) and fails unless only 22/80/443 are open | bash syntax checked; needs a Linux host |
| `scripts/deploy/verify_backup.sh` | `pg_restore --list` of a custom-format dump (optionally inside the environment's `db` container), checks all application tables are present, prints size and SHA-256; never restores | bash syntax checked; needs a dump and PostgreSQL client or running `db` |
| `scripts/deploy/check_capacity.sh` | Host memory/swap/disk/load plus live container memory and configured limits of named Compose projects; fails under `FIELDOPS_MIN_FREE_MIB`/`FIELDOPS_MIN_FREE_DISK_GIB` | bash syntax checked; needs the Docker engine |
| `scripts/smoke/smoke.py` | HTTPS readiness, private-path denial, cookie flags, API→inbox journey | passed against the local stack |

## Backups, persistence and capacity checks (prepared)

- Backup verification: `pg_restore --list <dump> | head` and the dump size are recorded per release; restoration is never automatic.
- Restart persistence: after `docker compose restart`, inbox and history counts must be unchanged (the T02 lifecycle test already proves this locally).
- Capacity: `docker stats --no-stream` for both projects must stay under the per-service `mem_limit`s (web unbounded by design; agent 192 MiB; monitoring ≤ 768 MiB) and the host must keep ≥ 2 GiB free before both environments share a host.
- Exposure scan: `nmap -sT -Pn <host>` (or `ss -ltn` on the host) must show only 22/80/443 open.

## Hosting evaluation (2026-11-12)

No hosting is approved or provisioned. Read-only checks of the development machine found an **enabled Azure subscription** signed in through the Azure CLI, an unauthenticated AWS CLI and a broken gcloud launcher. The lowest-cost option that fits the full stack (web, worker, PostgreSQL, agent, Prometheus, Alertmanager, Loki, Alloy, OTel collector, Jaeger, Grafana, proxy; roughly 3–4 GiB RAM per environment under the configured limits) is a single small Linux virtual machine with Docker Engine, hosting development and production as separate Compose projects, behind the per-environment Caddy edge with a DNS name. Using the Azure subscription would incur compute and public-IP charges and therefore requires explicit owner approval (action: create one Linux VM; cost: pay-as-you-go for the VM size chosen; rollback: deallocate and delete the VM). A split deployment across two hosts avoids the capacity check at higher cost. GitHub-hosted runners cannot serve as the deployment target. Nothing was created.

## Owner inputs required before T13 can start remotely

Hosting approval and access, a DNS name with TLS, the GitHub `development` and `production` environments (production with required reviewers), repository secrets `DEVELOPMENT_SSH_*`/`PRODUCTION_SSH_*`, variables `DEVELOPMENT_URL`, `PRODUCTION_URL`, `DEVELOPMENT_DEPLOY_ENABLED=true`, and a merged, validated main branch.
